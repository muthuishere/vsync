# `vsync` v0.10.0 — Spec

**Status:** design · target package `@muthuishere/vsync` · wire-format compatible with 0.9.x for unwrapped users; additive opt-in for wrapped users and rotators.

Two independent additions, shipped together because they share a branch (`claude/vsync-two-level-auth-wNlLN`) and a release:

1. **Two-level unlock** — the AES key in the OS keychain can be wrapped by a passphrase, where the passphrase lives in a **second keychain entry** that vsync reads but does not own. Anyone (the user, an ops script, an mTLS-equipped fetcher) can populate that entry; vsync just consumes it.
2. **Per-property rotators** — the vault folder gains a `.vsync.yml` config and a `scripts/` subfolder. `vsync rotate <PROP> --env=<env>` runs the configured script and writes its stdout back into `.env`.

Both are **opt-in** — repos that don't use them see no behavior change from 0.9.x.

---

## 1. Diff from 0.9.x

| | 0.9.x | 0.10.0 |
|---|---|---|
| Keychain entries per (repo, env) | 1 (AES key, raw base64) | 1 or 2 (AES key + optional passphrase) |
| AES key on-keychain encoding | raw base64 (~44 chars) | raw base64 **or** `RQE1`-wrapped envelope |
| `ConfigFile.encryption` | `{ salt }` | `{ salt, wrapped?: boolean }` |
| Failure modes for `loadEnvConfig` | `ConfigFileMissingError`, `KeyMissingError` | + `PassphraseMissingError` (wrapped key, no passphrase entry), `PassphraseWrongError` (unwrap failed) |
| Vault folder contents | freeform | freeform + optional `.vsync.yml`, `scripts/` |
| Subcommands | 10 | 12 (`+ set-passphrase`, `+ rotate`) |
| Dependencies | none (runtime) | `yaml` ^2 |

Migration: zero for unwrapped users. Wrap is opt-in via `vsync set-passphrase` post-init (which also re-wraps the on-keychain key). Existing S3 bundles are unchanged — wrap only affects key storage, not the bundle envelope.

## 2. Two-level unlock

### 2.1 Mental model

- **Level 1 (key entry)**: holds the AES-256 bundle key. Wrapped (`RQE1`) when level 2 is enabled, raw base64 otherwise.
- **Level 2 (passphrase entry)**: holds a UTF-8 string that unwraps level 1. Optional. vsync reads it but never "owns" its lifecycle — any process with keychain access for the user can write it.

Both entries live in the same `Bun.secrets` namespace (service `tools.vsync`). The "two levels" are operational: level 2 can be added, rotated, or wiped on a different cadence than level 1. Typical ops pattern: a startup script fetches the passphrase from an internal mTLS endpoint (or HashiCorp Vault, or wherever) and writes it to the keychain; on logout, a hook wipes only level 2.

### 2.2 Keychain layout

```
service: tools.vsync
  account: <repo>/<env>             → AES key (raw base64 OR RQE1 envelope)
  account: <repo>/<env>/passphrase  → passphrase string (UTF-8, ≥ 8 chars)
```

The trailing `/passphrase` segment is just a string; `Bun.secrets` treats accounts as opaque keys.

### 2.3 Key encoding — sniffing wrapped vs raw

The level-1 entry is either:

- **Raw** — base64-encoded 32-byte AES key, ~44 chars, characters limited to `[A-Za-z0-9+/=]`.
- **Wrapped** — bytes starting with the magic `RQE1` (`0x52 0x51 0x45 0x31`), base64-encoded for keychain storage.

`keychain.getKey` returns the raw string. A new `unwrapKeyIfNeeded(repo, env, raw, salt)` helper:

1. base64-decode `raw`.
2. If first 4 bytes are `RQE1`: look up `<repo>/<env>/passphrase`. If missing → `PassphraseMissingError`. Decrypt with `crypto.decrypt(bytes, passphrase, salt)`. Failure → `PassphraseWrongError`. Return the inner plaintext as the AES key (still base64).
3. Otherwise: return `raw` unchanged.

This means **the salt currently in `ConfigFile.encryption.salt` is reused** as the PBKDF2 salt for the keychain-key wrap. Same salt is already used for the S3 bundle; that's fine — the wrapped plaintext and the bundle plaintext have unrelated structures, no oracle.

### 2.4 `ConfigFile.encryption.wrapped`

New optional boolean:

```ts
encryption: { salt: string; wrapped?: boolean }
```

Absent or `false` → level 1 is raw, no passphrase lookup attempted. `true` → level 1 is `RQE1`; `loadEnvConfig` must resolve the passphrase entry.

The wrapped flag exists so `loadEnvConfig` can produce the right error *before* it tries to decrypt and gets a malformed-base64 failure with no actionable message. Sniffing the magic also works, but the flag is durable across import/export of share files.

### 2.5 New subcommand: `vsync set-passphrase <env>`

```
vsync set-passphrase <env> [--repo=<name>]
                           [--passphrase=<pp> | --passphrase-file=<path> | --passphrase-cmd=<cmd>]
                           [--unset]
                           [--interactive]
```

Behaviour:

| Mode | Action |
|---|---|
| First call with a passphrase, no `wrapped` yet | Generate a fresh wrap, encrypt level 1 with it, write the new `RQE1` to the AES key entry, write the passphrase to the level-2 entry, set `ConfigFile.encryption.wrapped = true`. |
| Subsequent call with a different passphrase | Read current level-1 (unwrap with old passphrase from level-2 entry, or prompt for it if absent), re-wrap with new passphrase, overwrite both entries. |
| `--unset` | Unwrap level 1, write the raw key back, delete level-2 entry, set `wrapped = false`. |
| Already wrapped, no flags, TTY | Prompt for new passphrase (re-key). |

Passphrase source precedence (same as today's `export`/`import`): explicit `--passphrase` > `--passphrase-cmd` (stdout, trimmed) > `--passphrase-file` (file contents, trimmed) > `$VSYNC_PASSPHRASE` > interactive prompt.

`set-passphrase` is a local-only operation. No S3 traffic, no audit-log row (the audit log records bundle access, not key-management metadata; that's by design).

### 2.6 Where existing commands plumb the passphrase

`loadEnvConfig(repo, env, opts?)` grows an `opts.passphrase?: string` escape hatch and an `opts.passphraseSource?: PassphraseSource` for callers that want to defer prompting until needed (e.g. `push`/`pull`/`sync`). When `wrapped === true` and `opts.passphrase` is unset, `loadEnvConfig` resolves the passphrase from level-2 keychain (default), or — if that's missing — via the same precedence ladder as `set-passphrase`.

Per-command flag wiring:

- `push`, `pull`, `sync`, `rotate`, `audit`, `versions`: accept `--passphrase`, `--passphrase-cmd`, `--passphrase-file`. No prompts in non-TTY by default (CI scripts populate the keychain entry beforehand, or pass the flag).
- `export`: when the source key is wrapped, unwrap before building the share blob — the `.share` file always contains the **raw** key (the share-file's own passphrase is the only protection there). This keeps the wire format of `.share` unchanged.
- `import`: writes the raw key to keychain by default. If the importer passes `--passphrase=<pp>` (a new, separate flag meaning "wrap this key on import"), the imported key is wrapped immediately and the level-2 entry is seeded. Mirrors `set-passphrase` semantics.

### 2.7 Errors

```
PassphraseMissingError(repo, env):
  "Key for <repo>/<env> is passphrase-wrapped, but no passphrase found in
   keychain (service=tools.vsync, account=<repo>/<env>/passphrase).
   Run `vsync set-passphrase <env>` to write it, or have your ops tool
   populate that keychain entry."

PassphraseWrongError(repo, env):
  "Failed to unwrap key for <repo>/<env> — passphrase in keychain entry
   <account> doesn't decrypt the stored RQE1 envelope. Either the key was
   re-wrapped with a different passphrase or the level-2 entry is stale.
   Run `vsync set-passphrase <env>` to reset, or have your ops tool refresh."
```

Both extend `Error` and follow the existing `ConfigFileMissingError` / `KeyMissingError` style of carrying actionable next-step text.

## 3. Per-property rotators

### 3.1 Layout

The vault folder grows two optional siblings:

```
infra/vault/<env>/
  .env                # existing
  .vsync.yml          # NEW — rotator map + future per-env knobs
  scripts/            # NEW — shebang scripts called by `vsync rotate`
    rotate-pg.sh
    rotate-api.sh
```

Both are encrypted + synced as part of the existing bundle (no changes to `archive.ts`, `push.ts`, `pull.ts`). Teammates `pull` and have everything.

### 3.2 `.vsync.yml` schema

```yaml
version: 1
rotators:
  POSTGRES_PASSWORD: scripts/rotate-pg.sh
  API_KEY: scripts/rotate-api.sh
```

- `version` is required, currently `1`.
- `rotators` is a map of env-property name → script path. Paths are resolved relative to the vault folder (`infra/vault/<env>/`). Absolute paths are rejected (would not travel via the bundle).
- Unknown top-level keys are preserved on read/write but ignored by `vsync rotate`. Future fields (timeouts, args) slot in without a schema bump.

YAML over JSON because rotator maps will be hand-edited and commented; YAML's `#` comments are friendlier than `// _comment` JSON hacks. Cost: one runtime dep (`yaml@^2`). Acceptable for the project's first runtime dep.

### 3.3 New subcommand: `vsync rotate <PROP> --env=<env>`

```
vsync rotate <PROP> --env=<env> [--repo=<name>]
                                [--dry-run]
                                [passphrase flags]
```

Steps:

1. Resolve repo, load env config (passphrase prompt happens here if wrapped).
2. Resolve vault folder (`resolveVaultFolder`), confirm it exists locally.
3. Read `<vaultFolder>/.vsync.yml`. If absent or no `rotators[PROP]` → exit 1 with: `"no rotator configured for <PROP> in <env>. Add it to <vaultFolder>/.vsync.yml"`.
4. Resolve the script path (relative to vault folder). Confirm it's executable; if not, exit 1 with a chmod hint.
5. Parse current `<vaultFolder>/.env` into KV pairs (reuse `src/envfile.ts` parser without inline-file expansion — we want literal values).
6. Spawn the script with:
   - **cwd** = the vault folder.
   - **process env** = a copy of `process.env` with every parsed key from `.env` overlaid, **plus** `VSYNC_ENV=<env>`, `VSYNC_PROPERTY=<PROP>`, `VSYNC_VAULT_DIR=<abs path>`.
   - **stdin** = closed.
   - **timeout** = 60s (configurable later via `.vsync.yml`).
7. Capture stdout. Trim trailing `\n`. Reject if empty or if it contains `\n` (multi-line stdout is ambiguous — error out with a hint).
8. Rewrite `<vaultFolder>/.env`: replace the line for `<PROP>` in place (preserving quoting style if any), or append it if absent. No other lines are touched.
9. Print: `rotated <PROP> in <env> (<old-len> chars → <new-len> chars). Run \`vsync push <env>\` to publish.`

`--dry-run` runs the script, captures stdout, and prints what it *would* write — but does not modify `.env`.

The script's stderr is forwarded to the user's terminal verbatim, so scripts can log progress. Non-zero exit → vsync aborts without touching `.env`, exit code propagates.

### 3.4 What the script can assume

- Its cwd is the vault folder; it can read sibling files (certs, JSON keys) directly.
- Every key in `.env` is in its process env. `DATABASE_URL`, `PGHOST`, `PGUSER`, `OLD_PASSWORD` (the value being rotated) — all present.
- `VSYNC_PROPERTY` tells it which key the user asked for, so one script can be aliased to multiple properties if needed.
- It must print exactly one line to stdout: the new value. Trailing newline OK, embedded newlines rejected.
- It is responsible for any live-system propagation (SSH to the DB, call the cloud SDK, etc.) — vsync only touches the file.

Half-failure semantics: scripts that mutate the live system before printing stdout own the half-failure problem. Recommended pattern in the script is "generate → propagate → verify → echo" so the value vsync sees is the one that's already in production. vsync does not implement a transactional protocol around this in v0.10.

### 3.5 What `vsync rotate` does *not* do

- Does not auto-push. Symmetric with the rest of vsync.
- Does not re-encrypt or touch the bundle. The vault folder is plain on disk; `push` handles re-encryption later.
- Does not schedule rotations. Cron/Taskfile/whatever the user already uses runs `vsync rotate` periodically.
- Does not validate the new value's format. Scripts return arbitrary strings.
- Does not provide a rollback. Previous values are recoverable from `vsync versions` + `vsync pull` to a backup.

## 6. Out of scope for v0.10

- mTLS, HTTP, or any network code for fetching the passphrase. vsync reads keychain, full stop.
- Rotation scheduling, alerting, drift detection. User's existing scheduler runs `vsync rotate`.
- Multi-property atomic rotation (one script writing several env keys). Stdout is a single value. If needed later, a v0.11 spec can extend with a structured-stdout mode.
- Rollback / rotation history beyond what `vsync versions` already provides.
- Cross-platform `chmod +x` on the rotator scripts during pull. Users on Windows handle exec bits themselves.
